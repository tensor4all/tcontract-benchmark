# Timing-v2 layout: which tree owns what

This repository carries two generations of the campaign at once. The historical
timing-v1 evidence and its scripts are unchanged and stay authoritative for the numbers
they recorded; the new timing-v2 campaigns live beside them and are owned by the shared
toolkit.

## Legacy timing-v1 (untouched)

Owned by this repository's own copies of the recorder/report/index scripts and by the
committed evidence:

- `data/results/**` — raw v1 runs, one directory per `(profile, suite, timestamp)`.
- `result/**` — v1 pages and the generated `result/INDEX.md`.
- `scripts/{record_run,report_run,validate_run,gen_index,publish_report}.py`,
  `schemas/*.json` — the v1 pipeline. CI runs `validate_run.py` and `gen_index.py --check`.
- `benchmarks/suites/{tcbench,per-shape}.yaml` — the v1 declarations.
- `pins/tcontract-rs.rev` — the v1 reference revision.
- `scripts/setup_extern_deps.sh`, `scripts/build_for_tprims_rev.sh` — shared helpers.

`benchmarks/profiles.yaml` is shared: a profile is a fact about a machine, and both
generations name `zen5-cpu`.

## Timing-v2 (toolkit-owned)

Owned by `campaign_toolkit`, pinned in `pins/campaign-toolkit.rev` and in
`requirements.txt`:

- `benchmarks/campaign-tcbench.yaml`, `benchmarks/campaign-per-shape.yaml` — the two
  descriptors, one per harness (`tcbench`, `lukbench`). Select one with
  `CAMPAIGN_DESCRIPTOR=benchmarks/campaign-<id>.yaml`.
- `benchmarks/suites-v2/{tcbench,per-shape}.yaml` — the frozen declarations, generated
  from the pinned harness's own census (see below).
- `data/v2-results/<campaign>/**` — raw v2 runs.
- `result-v2/<campaign>/**` and `result-v2/<campaign>/INDEX.md` — v2 pages and index,
  generated by `python3 -m campaign_toolkit.gen_index --write`.
- `pins/tcontract-rs-v2.rev` — the measured revision both v2 campaigns pin.
- `scripts/gen_suite_from_census.py` — the suite generator.
- `scripts/setup_v2_extern_deps.sh` — materialise `extern/tcontract-rs-v2`.

`result/README.md` carries a links-only pointer to the two v2 indexes. `result/INDEX.md`
is the v1 index and is never rewritten by the v2 pipeline.

## Regenerating a suite

Build the pinned harness without TBLIS (the `blas` feature is what makes the `ttgt` row
measurable), then run the generator:

```sh
scripts/setup_v2_extern_deps.sh
BENCH_FEATURES=blas scripts/build_for_tprims_rev.sh extern/tcontract-rs-v2 /tmp/pin.env tcbench lukbench
python3 scripts/gen_suite_from_census.py --harness tcbench \
    --binary target/tcontract-rev/7738bf43a068/release/tcbench \
    --revision "$(git -C extern/tcontract-rs-v2 rev-parse HEAD)" \
    --out benchmarks/suites-v2/tcbench.yaml
```

The generator runs the harness's untimed `verify` census at each declared thread budget,
folds it into a suite, and refuses to write anything whose census does not equal the
product the declaration would require. The emitted file is committed and frozen;
re-running against the same binary is byte-identical.

## Checking the declarations

The declaration check is the toolkit's; put its checkout on the path (or install
`requirements.txt`) and select a descriptor:

```sh
CAMPAIGN_DESCRIPTOR=benchmarks/campaign-tcbench.yaml \
  PYTHONPATH=../campaign-toolkit python3 -m campaign_toolkit.declarations --root .
```

Both descriptors share `benchmarks/suites-v2`, so each is checked against both suites and
their `engines` map is the union of the rows the two suites may select.
